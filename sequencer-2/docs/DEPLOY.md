# Deploying seq-2 to Grid hardware

How the sequencer runs on a real Grid **VSN1R** module, and how to regenerate +
upload it. Knowledge distilled from the proven "Note Step Sequencer" profile
(`~/Documents/grid-userdata/configs/Note Step Sequencer *.json`).

## Grid config model (what a profile is)

A **profile** is a JSON file (`grid-userdata/configs/<name>.json`) describing one
module. Its `configs` array holds **control elements**; each element has
**events**, and each event holds a **Lua string ≤ 900 chars**.

- Elements are addressed by **`controlElementNumber`**. On VSN1R: physical
  buttons/keyswitches/encoder are `0..13`, the screen is `13`, and the **system
  element is `255`**.
- **Event ids** seen in the proven profile: `0` = Init/Setup, `2` = Encoder,
  `3` = Button, `7` = Endless (push-encoder), `8` = Screen draw, `4`/`6` = misc
  (page/timer). (Full list: docs.intech.studio → *element referencing*.)
- Setup vs callback within one event string is split by comment markers:
  `--[[@cb]]` (callback), `--[[@sbc]]`/`--[[@sec]]`/`--[[@sen]]`/`--[[@sglc]]`
  (button/encoder/endless/led setup, run once).
- **Cross-element calls:** `gis(module, element, "code")` runs code elsewhere
  (e.g. push to a satellite EN16). **Draw API:** `self:draw_*` + `self:draw_swap()`
  (the grid-wasm `ggd*` are harness aliases). **MIDI:** `grxm(...)` arms rx,
  `gms(ch, status, p1, p2)` sends. **Backlight:** `glsb(255)`.

## How seq-2 is driven (the stable hooks)

`tools/gen_profile.py` encodes these; they rarely change.

**Element 255, event 0 — system setup** (521/900 chars):
```lua
SEQ=require("seq2") SEQB=require("seq2b") ENGINE=SEQB.engine MIDIRX=SEQB.midirx
function loadUI() if not CTL then CTL=require("seq2_ctl").control
  local U=require("seq2_ui") DRAW=U.draw LEDS=U.leds CTL.bind(ENGINE,SEQ) end
  return CTL end
ENGINE.init({trackCount=2})                            -- 2 tracks: heap budget
grxm(2,3)                                              -- arm MIDI rx
self.rtmrx_cb=function(self,h,t) MIDIRX.handle(t, gms) end
```
`MIDIRX.handle` (in `seq2b`) runs `Engine.onPulse()` on each `0xF8` clock and
emits `engine.out` via `gms`; `0xFA`/`0xFC` = start/stop. Patterns are
generated lazily by `control.bind` on the first input/draw (which pulls
`seq2_gen`), NOT at setup — boot loads only the two Core bundles.

**Element 13 — screen:** event 0 `glsb(255)` (backlight), event 8
`loadUI() DRAW(self,ENGINE,CTL) C=(C or 0)+1 if C%4==0 then LEDS(ENGINE,CTL)end`
(lazy UI load, text-only draw, LED pass throttled to every 4th frame).

## Lean device build (why 5 small text bundles)

The module watchdog reboots on loading a chunk that is too big, and the heap
ceiling is ~130 KB with a ~91 KB boot baseline (seq-1 measurements). The
proven seq-1 discipline, copied here: **plain TEXT bundles ≤ ~10 KB each**,
loaded sequentially, UI lazy. Device-code rules enforced in
`tests/dist_smoke.lua`: **no `collectgarbage`, no `package.loaded`
manipulation, no `string.format`** (absent from the Grid Lua build). Earlier
seq-2 attempts that broke these rules (15.6 KB single text chunk,
GC-on-mode-switch) failed to boot on device.

Cuts made for the lean build: text-only screen (no piano roll; playhead shown
as `pos t/n` text), SONG page UI removed (engine song API remains), LED pass
slimmed + throttled, 2 tracks.

## Artifacts (generated by the build)

```
lua5.4 tools/build.lua          # -> 5 text bundles in dist/ (see below)
python3 tools/gen_profile.py --install   # -> dist/Sequencer Magnetar.json AND grid-userdata/configs/
```

- **`dist/seq2.lua`** (10.3 KB) — Core data model: event, scales, fx, rack,
  pattern, track. Required at setup. Self-contained.
- **`dist/seq2b.lua`** (4.4 KB) — Core runtime: sequence, engine, midi_rx.
  Required at setup, right after `seq2`.
- **`dist/seq2_ctl.lua`** (8.7 KB) — control (staged params, modes). Lazy:
  first input/draw. Pulls `seq2_gen`.
- **`dist/seq2_ui.lua`** (6.9 KB) — text-only draw + LED pass. Lazy.
- **`dist/seq2_gen.lua`** (1.9 KB) — generator. Lazy (via seq2_ctl).
- **`dist/Sequencer Magnetar.json`** / installed copy — the profile (event scripts).
  `files[]` is empty by design — the `.lua` bundles are uploaded separately.
- All bundles are PLAIN TEXT on purpose (the Grid editor rejects binary
  uploads; the device compiles text at load). `--bytecode` exists as a
  fallback experiment flag, smaller resident chunks but upload-unfriendly.

## Upload / run (Grid editor)

1. In the Grid editor, open the VSN1R module's code/file storage and **upload
   the 5 bundles under their exact require names**: `dist/seq2.lua` as `seq2`,
   `dist/seq2b.lua` as `seq2b`, `dist/seq2_ctl.lua` as `seq2_ctl`,
   `dist/seq2_ui.lua` as `seq2_ui`, `dist/seq2_gen.lua` as `seq2_gen`.
2. **Load the "Sequencer Magnetar" profile** onto the module (it's already in
   `grid-userdata/configs/`).
3. Route a **MIDI clock** into the module (e.g. Ableton → module) and the
   module's **MIDI out** to a synth or back into Ableton.
4. Press **play** in Ableton: the engine is clocked, notes go out on ch 1/2,
   and the screen shows the text status view.

## Regenerate after code changes

```
lua5.4 tools/build.lua && python3 tools/gen_profile.py --install
```
Re-upload `seq2` / `seq2_ui` if the Core/UI changed; reload the profile only if
the event scripts changed.
 
## Caveats / open

- **Full element skeleton:** the profile CLONES `tools/vsn1r_template.json` (the
  proven profile's 15 elements) and overrides only 255 (setup) + 13 (screen). A
  partial profile (missing elements) makes the editor throw
  `Cannot read properties of undefined (reading 'events')` on load — hence the clone.
- **Controls (wired):** logic is in `src/app/control.lua` (UI bundle); event
  scripts forward (`loadUI().key(0,self:bst()==127)`). Control is on **8
  keyswitches (0-7) + 4 small buttons (9-12) + the encoder**. Map (full table
  in `src/app/control.lua` header):
  - **Small buttons 9-12** (dedicated, no chords): **9 = BACK**, **10 = ENTER**,
    **11 = NAP** (toggle, current track), **12 = COMMIT** (apply staged).
  - **GLOBAL:** KS7 = MODE cycle (PLAY → STEP → SEQ).
  - **PLAY** (staged): KS0-4 select HITS/KEY/SCALE/SPREAD/VEL; KS5 = AUTO-REROLL;
    KS6 = TRACK. Encoder turn STAGES the param, encoder click = REROLL. ENTER →
    SETUP (full grid, BACK returns).
  - **STEP** (live): encoder turn = step cursor, click = field (PITCH/LEN/VEL);
    KS0 add note, KS1 delete, KS2/3 octave, KS4/5 field value ±, KS6 track.
  - **SEQ** (slot picker): KS0-3 pick track, encoder = slot, KS5 = mute, click =
    next sequence.
  - Generation runs in `control.bind` (lazy, on first input/draw), not in setup.
  - `control.frame()` (called from the draw event) services auto-reroll off the
    hot path.
- Verify the exact `grxm(2,3)` args and MIDI routing on device — copied verbatim
  from the proven profile.

## LED model (decoupled from control)

**Path chosen: (2) — plainest element mode; LED lighting is its own task.**
All control elements ship in their plainest event mode — plain
`bst()`/`epva()` callbacks, with no `bmo` toggle/momentary and no element-level
`glc`/`glp` colour setup. `bmo` would only buy LED brightness tied to
toggle/momentary state; we reject that coupling so element behaviour never
carries logic.

- **Renderer:** `src/hal/leds.lua` (bundled in `seq2_ui`) exports `leds(eng, ctl)`.
  It is called from the **screen draw event** (el 13 ev 8, throttled to every
  4th frame), off the pulse hot path, and drives every element's LED via the
  Grid global `led_color(element, led, r, g, b, brightness)` (LED index **2** —
  the primary LED the proven seq-1 profiles light in `../sequencer-1/configs/*.lua`;
  the brightness ceiling is `led_value(element, led, brightness)` if needed).
- **Single source of truth:** `M.compute(eng, ctl, frame)` returns a pure table
  `lit[0..12] = {r,g,b}` derived only from `CTL.mode/setup`, `track`,
  `sel`, seq-track selection, `nap.armed` + `nap.muted`, `auto.armed`, `dirty`,
  and the current sequence's mute mask. No LED state is stored independently.
- **Blink/breathe** (nap armed, commit-pending) is computed in Lua from a frame
  tick (`frame % 40 < 20`), never from firmware element behaviour.
- Palette: mode = KS7 colour (PLAY orange / STEP cyan / SEQ purple); selected
  item = white; AUTO = green; NAP = red (blinks while armed+awake, steady while
  napping); COMMIT = orange (blinks while `dirty`); mute = red.

**The one exception** to "no element setup" is the encoder turn event, which
keeps its `--[[@sen]] self:epmo(1)…` relative-mode setup — that's the *only*
way `epva()` returns a ±1 delta, and it is encoder physics, not toggle/LED logic.

## Hardware quirks found on-device

- **Encoder = relative.** The endless push-encoder (el 8, event 7) is set to
  relative mode via `--[[@sen]] self:epmo(1)…`; a turn sends 63 (CCW) / 65 (CW),
  so the callback delta is `self:epva()-64` (±1). If it ever behaves like an
  absolute knob, check the endless element's mode in the editor UI.
- **Small-button events.** Small buttons 9–12 fire their press event exactly like
  keyswitches 0–7 (`self:bst()==127`). All control elements ship in plainest
  mode (no `bmo`) — see "LED model" above; LED feedback is rendered separately
  via `led_color()`.
